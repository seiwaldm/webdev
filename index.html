Auszeichnungssprachen: Text mit Struktur

Eine Auszeichnungssprache (Markup Language) strukturiert Text: Sie markiert, was Überschrift, Liste oder Datenfeld ist. Wie es aussieht, entscheidet erst das Programm, das den Text darstellt.

  • HTML (Hypertext Markup Language): die Sprache jeder Webseite.
  • Markdown (MD): schlanke Syntax für Notizen und Dokumentation, heute eine der beliebtesten Auszeichnungssprachen.
  • XML (Extensible Markup Language): Daten mit selbst erfundenen Tags.
  • YAML („YAML Ain’t Markup Language“, früher „Yet Another Markup Language“): vor allem für Konfigurationsdateien.
README.md

Das Terminal und die PATH-Variable

Im Terminal steuerst du den Computer mit Textbefehlen. Man spricht auch von der CLI (Command Line Interface). Viele Entwicklerwerkzeuge haben gar keine grafische Oberfläche.

  • Tippst du git init, sucht die Shell ein Programm namens git. Sie durchsucht dabei nicht die ganze Festplatte, sondern nur die Ordner in der Umgebungsvariable PATH.
  • Ein Installationsprogramm trägt seinen Ordner in PATH ein. Erst dann ist der Befehl im Terminal überall verfügbar.
  • Erscheint command not found, ist das Programm nicht installiert oder sein Ordner fehlt in PATH. Nach einer Installation hilft oft ein neues Terminalfenster: PATH wird beim Start eingelesen.
Probier es aus

echo $PATH (macOS, Linux) oder $env:Path (Windows PowerShell) zeigt deine PATH-Ordner.

Git & GitHub: vom Ordner ins Repository

Git speichert die Geschichte eines Projekts als Folge von Schnappschüssen, den Commits. GitHub ist ein Onlinedienst, der Git-Repositories speichert und teilbar macht.

  1. Im Projektordner im Terminal git init ausführenCLI
  2. In GitHub Desktop: File › Add Local Repository …GUI
  3. Änderungen beschreiben, dann Commit to master (bzw. main)GUI
  4. Push origin lädt die Commits zu GitHub hochGUI
Merksatz

Commit = Schnappschuss auf deinem Rechner. Push = Upload zu GitHub. Ohne Push liegt alles nur lokal.

Fetch & Pull: Änderungen von GitHub holen

Arbeiten mehrere Personen am selben Repository, oder du auf mehreren Rechnern, liegen auf GitHub bald Commits, die du lokal noch nicht hast. Zwei Befehle holen sie ab:

Fetch git fetch · Fetch origin
Fragt bei GitHub nach und lädt neue Commits in dein lokales Repository. Deine Dateien bleiben, wie sie sind. Ungefährlich, jederzeit möglich.
Pull git pull · Pull origin
Fetch und danach Merge: Die neuen Commits werden in deinen Branch übernommen, die Dateien im Projektordner ändern sich.
Faustregel

Vor dem Arbeiten pullen, vor dem Pushen pullen. Liegen auf GitHub Commits, die du nicht hast, lehnt Git deinen Push ab. Haben zwei Personen dieselben Zeilen geändert, entsteht ein Merge-Konflikt, den du von Hand auflöst.

Von der URL zur Website: DNS und HTTP

Bevor dein Browser eine Seite laden kann, braucht er die IP-Adresse des Webservers. Den Domainnamen übersetzt das DNS (Domain Name System), wie ein Telefonbuch.

  1. Der Browser fragt den DNS-Server nach der IP von www.beispiel.atDNS
  2. Der DNS-Server antwortet mit der IP-AdresseDNS
  3. Der Browser schickt eine HTTP-Anfrage an diese IPHTTP
  4. Der Webserver antwortet, zuerst meist mit der index.htmlHTTP
Vorher: die Betreiberin der Website

Sie registriert einen eigenen Domainnamen und legt einen DNS-Eintrag an, der den Namen in die IP-Adresse ihres Webservers übersetzt.

Statisch oder dynamisch?

Statische Website 1990er
Fertige .html-Dateien werden auf den Webserver hochgeladen. Jeder Aufruf liefert dieselbe Datei, egal wer fragt.
Dynamische Website ab 2000
Die Inhalte liegen in einer Datenbank. Bei jedem Aufruf holt ein Skript in einer serverseitigen Sprache (PHP, Python, JavaScript …) die Inhalte und bettet sie in eine HTML-Seite ein. So kann jede Person etwas anderes sehen.
Für den Browser kein Unterschied

Er bekommt in beiden Fällen fertiges HTML. Ob die Seite schon vorlag oder eben erst gebaut wurde, sieht er nicht. Die DNS-Auflösung davor ist ebenfalls gleich.

Eine dynamische Website ist ein Restaurant

Wer bei einer dynamischen Website was tut, lässt sich mit einem Restaurantbesuch erklären:

Im RestaurantIm Web
Gast=Webbrowser (Client)
Kellner=Webserver
Köchin=serverseitige Sprache: PHP, Python, JavaScript …
Vorratskammer=Datenbank
Rezept=HTML-Template (Vorlage)
Gericht=fertige HTML-Seite

Single-Page Applications

Eine SPA lädt beim ersten Aufruf eine einzige HTML-Seite samt JavaScript. Danach tauscht JavaScript nur die Teile aus, die sich ändern, und holt neue Daten bei Bedarf vom Server.

  • Eine klassische Website lädt bei jedem Klick eine komplett neue Seite: kurz weiß, Scrollposition weg, alles neu.
  • Eine SPA fühlt sich an wie eine Desktop- oder Handy-App: schnell und flüssig, ohne Neuladen.
  • Gebaut wird sie mit JavaScript-Frameworks wie React, Vue, Angular oder Svelte. Dominant seit den 2010er-Jahren.
  • Der Preis: Mehr Arbeit passiert im Browser, und der erste Aufruf lädt mehr JavaScript.

Progressive Web Apps

Damit Webapps Handy-Apps möglichst nahekommen, gibt es den PWA-Standard. Eine PWA lässt sich installieren, funktioniert offline, sendet Push-Benachrichtigungen und nutzt bestimmte Gerätefunktionen. Drei Voraussetzungen muss sie erfüllen:

Voraussetzung 1

Web-App-Manifest

Die Datei manifest.json enthält Grundinformationen über die App: Name, Icons, Start-URL, Darstellung.

{
  "name": "Mühle",
  "start_url": "/",
  "display": "standalone",
  "icons": [ … Bilder … ]
}
Voraussetzung 2

Service Worker

Eine JavaScript-Datei, die im Hintergrund des Browsers läuft, unabhängig von der geöffneten Seite, sogar wenn der Tab geschlossen ist. Sie ermöglicht Caching, Offline-Betrieb und Push-Benachrichtigungen.

Voraussetzung 3

HTTPS

Die App muss über eine verschlüsselte Verbindung ausgeliefert werden. Das sichert Sicherheit und Integrität: Niemand kann unterwegs mitlesen oder fremden Code einschleusen.

Gut zu wissenService Worker laufen nur über HTTPS. Ausnahme beim Entwickeln: localhost.

Der Service Worker: offline dank Cache

  • Der Service Worker sitzt wie ein Proxy zwischen Webapp und Netzwerk und fängt jede Anfrage ab.
  • Online holt er die Antwort aus dem Netz und legt eine Kopie im Cache ab.
  • Offline antwortet er aus dem Cache. Die App läuft weiter, als wäre nichts passiert.
sw.js · Strategie „Netz zuerst, sonst Cache“
self.addEventListener('fetch', (event) => {
  event.respondWith(
    fetch(event.request)
      .then((res) => {
        const copy = res.clone();
        caches.open('v1')
          .then((c) => c.put(event.request, copy));
        return res;
      })
      .catch(() => caches.match(event.request))
  );
});

Komponenten: die Lego-Bausteine einer Webapp

Frontend-Frameworks folgen einigen Architekturprinzipien, die eine möglichst gute User Experience (UX) ermöglichen. Das erste: Eine Komponente kapselt HTML, CSS und JavaScript in einer Einheit, etwa in einer .svelte-Datei.

  • Jede Komponente lässt sich unabhängig entwickeln, testen und warten.
  • Komponenten werden verschachtelt: Die App enthält ein Board, das Board 24 BoardPoints. So entsteht ein Baum.

Deklarativ und reaktiv

Imperativ beschreibst du jeden einzelnen Schritt: Element suchen, Text ändern, Klasse setzen. Deklarativ beschreibst du nur, wie die Oberfläche aussehen soll. Um die Umsetzung kümmert sich das Framework.

  • Dabei kommt Reaktivität ins Spiel: Ändert sich der Zustand (State) der Anwendung, aktualisiert das Framework die Benutzeroberfläche (UI) automatisch.
  • Du änderst nur count. Überall, wo {count} steht, erscheint sofort der neue Wert.
  • Das Framework übersetzt die Templates (HTML) der Komponenten in die eigentliche Oberfläche.

Zwei-Wege-Datenbindung

Funktioniert die Aktualisierung auch in die andere Richtung, spricht man von bidirektionaler Datenbindung (two-way data binding).

  • State → UI: Ändert das Programm den Wert, zeigt die Oberfläche ihn sofort an.
  • UI → State: Interagiert die Person mit der Oberfläche, etwa durch Tippen, wird der State sofort angepasst, und alles, was ihn verwendet, zieht nach.
  • In Svelte genügt dafür bind:value.
Greeting.svelte
<script>
  let name = $state('Anna');
</script>

<input bind:value={name} />
<p>Hallo {name}!</p>

Logikbausteine: Listen und Bedingungen

In den Templates der Komponenten stehen einfache Logikbausteine: Schleifen, um Listen darzustellen, und Bedingungen, um Teile der Oberfläche ein- und auszublenden.

  • {#each} wiederholt ein Stück HTML für jedes Element einer Liste.
  • {#if} … {:else} zeigt Teile nur, wenn eine Bedingung erfüllt ist.
  • Ändert sich die Liste, passt das Framework die Oberfläche automatisch an. Auch das ist Reaktivität.

Props nach unten, Events nach oben

Props (Eigenschaften)
Daten, die eine übergeordnete Komponente an eine untergeordnete weitergibt.
Events (Ereignisse)
Benachrichtigungen, die eine untergeordnete Komponente an die übergeordnete sendet, etwa wenn jemand klickt.
Svelte 5: Events sind Funktionen, die als Prop übergeben werden
<!-- Board.svelte (Eltern) -->
<BoardPoint
  stone={stones[i]}
  onplace={() => place(i)} />

<!-- BoardPoint.svelte (Kind) -->
<script>
  let { stone, onplace } = $props();
</script>
<button onclick={onplace}>{stone}</button>

Node.js: JavaScript außerhalb des Browsers

Normalerweise läuft JavaScript in einer Sandbox im Browser: Es darf die Seite verändern, aber nicht auf deine Dateien zugreifen. Seit ca. 2010 gibt es mit Node.js eine Laufzeitumgebung (Runtime Environment), mit der JavaScript auch serverseitig läuft.

  • Gleiche Sprache, gleiche Engine (V8 aus Chrome), andere Umgebung.
  • Node.js darf Dateien lesen und schreiben, Server starten und andere Programme aufrufen. Eine Webseite (DOM) gibt es dort dafür nicht.
  • Damit wird JavaScript zur serverseitigen Sprache. Auch fast alle Werkzeuge der Webentwicklung laufen auf Node.js: Vite, pnpm, Strapi …
  • Installation über nodejs.org, am besten die LTS-Version (Long Term Support).

Paketmanager: npm und pnpm

Kaum ein Projekt schreibt alles selbst. Fertige Bausteine heißen Pakete (packages). Ein Package Manager lädt sie herunter, löst Abhängigkeiten auf und hält sie aktuell.

  • npm (node package manager) kommt mit Node.js mit und ist der Standard.
  • pnpm ist eine modernere, inzwischen sehr beliebte Variante: schneller und sparsamer. Jedes Paket liegt nur einmal in einem zentralen Speicher und wird in die Projekte verlinkt.

package.json: der Steckbrief des Projekts

Die Datei package.json beschreibt die Anwendung selbst, listet alle Abhängigkeiten (dependencies) und enthält Skripte, die wiederkehrende Aufgaben automatisieren.

  1. Name, Version und weitere Infos zur App (Autor, Lizenz …)
  2. Skripte: pnpm dev startet die App zum Entwickeln, pnpm build erstellt die Produktionsversion
  3. dependencies: werden beim Ausführen gebraucht (runtime) und laufen im Browser mit
  4. devDependencies: nur beim Entwickeln und Bauen (build time). Sogar Svelte selbst: Es wird beim Build zu normalem JavaScript kompiliert
node_modules

pnpm install lädt alles nach node_modules. Der Ordner kommt nie zu GitHub, er lässt sich jederzeit neu erzeugen. Exakte Versionen stehen in pnpm-lock.yaml.

Ein Backend aufsetzen: Strapi

Strapi ist ein Headless CMS auf Basis von Node.js: Inhalte werden in einem Admin-Panel gepflegt, das Frontend holt sie als JSON über eine API. „Headless“ heißt: ohne eigenes Frontend.

  1. Installation starten, die CLI führt mit Fragen durchpnpm create strapi
  2. Build-Skripte blockiert? In das Installationsverzeichnis wechselncd my-strapi-project
  3. Installation erneut versuchen. Scheitert in der Regel ebenfallspnpm install
  4. Build-Skripte manuell freigebenpnpm approve-builds
  5. Strapi startenpnpm develop
Warum blockiert pnpm?

Manche Pakete führen beim Installieren eigene Skripte aus. pnpm erlaubt das seit Version 10 aus Sicherheitsgründen nur nach Freigabe.

Die Ordnerstruktur eines Frontend-Projekts

So sieht ein typisches Svelte-Projekt aus, hier das Mühle-Spiel. Klick dich durch die Ordner und Dateien.

  • .vscode: Einstellungen für den Editor VS Code
  • node_modules: alle Abhängigkeiten, die in der package.json aufgelistet sind
  • public: statische Dateien, die der Browser direkt unter ihrem Pfad lädt
  • src: der Quellcode. Mit lib für eigene Komponenten und Hilfsfunktionen
  • Im Hauptordner: Konfigurationsdateien für Vite, Svelte und TypeScript

Wie die App startet: die Einstiegspunkte

Eine SPA hat genau eine HTML-Seite. Den Rest erledigt JavaScript. Diese Dateien lädt der Browser als Erstes:

  1. index.html im Hauptordner: ein leeres <div id="app"> und ein Script-Tag
  2. main.ts: der Einstiegspunkt für TypeScript. Lädt die globalen Stile aus app.css und hängt die App ein
  3. App.svelte: die Hauptkomponente. Sie importiert die anderen Komponenten und zeigt sie an
  4. Die Komponenten aus lib/components bauen die Oberfläche zusammen
Und Vite?

Browser verstehen weder .ts noch .svelte. Vite übersetzt die Dateien beim Entwickeln im Hintergrund in normales JavaScript und bündelt sie beim Build.

Der Store: eine Quelle der Wahrheit

Die Datei store.svelte.ts enthält den Zustand (State) der App: alle Daten, die sich im Lauf der Zeit ändern, etwa Spielstand, Ergebnisse und Einstellungen.

  • Er ist die zentrale Datenquelle, die Single Source of Truth: Jede Information gibt es genau einmal.
  • Komponenten lesen daraus und ändern ihn über Funktionen wie place(). Dank Reaktivität sehen alle sofort den neuen Stand. Ohne Store hätte jede Komponente eine eigene Kopie, und die Kopien laufen auseinander.
src/lib/game/store.svelte.ts (vereinfacht)
export const game = $state({
  turn: 'weiß' as 'weiß' | 'schwarz',
  rest: { weiß: 9, schwarz: 9 },
  phase: 'setzen'
});

export function place(i: number) {
  game.rest[game.turn]--;
  game.turn = game.turn === 'weiß' ? 'schwarz' : 'weiß';
}

Vibe Coding und Agentic Engineering

Vibe Coding
Du beschreibst in natürlicher Sprache, was du willst, und eine KI schreibt den Code.
Agentic Engineering
Ein KI-Agent arbeitet selbständig in mehreren Schritten. Du steuerst, prüfst und testest wie eine Ingenieurin oder ein Ingenieur.
  • In VS Code passiert das in erster Linie in der neuen Agent View, mit GitHub Copilot.
  • Der Agent arbeitet in einer Schleife: Kontext lesen, planen, handeln (Tools aufrufen), prüfen. Bis die Aufgabe erledigt ist.
  • Du bleibst verantwortlich: Code lesen, verstehen, testen. Ein Agent kann sich irren, sehr überzeugend.

Die Coding Harness

Ein Sprachmodell (LLM, Large Language Model) allein erzeugt nur Text. Erst die Harness (engl. für „Geschirr“, wie bei einem Zugpferd) macht daraus einen Agenten: Sie liefert Anweisungen, Kontext und Werkzeuge und führt seine Aktionen aus.

In der Agent View von VS Code passt du deine Harness an:

  • Instruktionen: Regeln für dein Projekt, etwa in .github/copilot-instructions.md oder AGENTS.md
  • Tools: welche Werkzeuge der Agent benutzen darf, z. B. Dateien, Terminal, Suche
  • Kontext: welche Dateien und Informationen das Modell zu sehen bekommt
  • MCP-Server: zusätzliche Tools von außen, mehr dazu auf der nächsten Folie

MCP: das Model Context Protocol

MCP ist ein von Anthropic entwickelter Standard. Über MCP können Chatbots und Agenten (LLMs) auf zusätzliche Tools zugreifen, die sie zu Expert:innen in einem bestimmten Themenbereich machen.

  • Ein MCP-Server bietet Tools an, z. B. „Doku durchsuchen“ oder „Datenbank abfragen“.
  • Der MCP-Client in VS Code verbindet den Agenten mit beliebig vielen Servern.
  • Ein offener Standard: Ein Server funktioniert mit jedem Programm, das MCP spricht. Oft verglichen mit USB-C.
.vscode/mcp.json
{
  "servers": {
    "svelte": {
      "type": "http",
      "url": "https://mcp.svelte.dev/mcp"
    }
  }
}

Teste dich selbst

Erst im Kopf beantworten, dann die Karte öffnen.

KAP 1Warum erscheint „command not found“?

Die Shell hat in keinem Ordner der PATH-Variable ein passendes Programm gefunden: Es ist nicht installiert, oder sein Ordner fehlt in PATH.

KAP 2Welche vier Schritte braucht es von der URL zur Seite?

1. DNS-Anfrage nach der IP, 2. DNS-Antwort mit der IP, 3. HTTP-Request an den Webserver, 4. HTTP-Response mit HTML, CSS und JavaScript.

KAP 2Wer ist im Restaurant die Köchin, wer die Vorratskammer?

Die Köchin ist die serverseitige Sprache (PHP, Python, JavaScript …), die Vorratskammer die Datenbank. Das Rezept ist das HTML-Template.

KAP 3Welche drei Voraussetzungen muss eine PWA erfüllen?

Ein Web-App-Manifest (manifest.json), einen Service Worker und die Auslieferung über HTTPS.

KAP 4Wie reden Eltern- und Kind-Komponente miteinander?

Über Props (Daten von oben nach unten) und Events (Benachrichtigungen von unten nach oben).

KAP 5dependencies oder devDependencies: Wohin gehört Vite?

Zu den devDependencies. Vite wird nur beim Entwickeln und Bauen gebraucht (build time), nicht beim Ausführen der fertigen App (runtime).

KAP 6Was bedeutet „Single Source of Truth“?

Jede Information liegt genau einmal an zentraler Stelle, im Store. Alle Komponenten lesen von dort und ändern ihn nur über dafür vorgesehene Funktionen.

KAP 7Was ist ein MCP-Server?

Ein Programm, das einem LLM über das Model Context Protocol zusätzliche Tools anbietet, z. B. Doku-Suche oder Datenbankzugriff.

Das Wichtigste in Kürze

  • Das Web ist ein Frage-Antwort-Spiel: DNS übersetzt Namen in Adressen, HTTP liefert die Seiten.
  • Statisch, dynamisch, Single-Page App: Heute stehen SSG, SSR und CSR nebeneinander. Gewählt wird je nach Anwendungsfall, moderne Frameworks kombinieren sie (Hybrid).
  • Frameworks denken in Komponenten, State und Reaktivität. Props fließen nach unten, Events nach oben.
  • Terminal, Git, Node.js und pnpm sind das tägliche Handwerkszeug.
  • KI-Agenten beschleunigen die Arbeit. Verstehen und prüfen musst du den Code trotzdem selbst.
